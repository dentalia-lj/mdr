### Out-of-band — Corpus-first cold start + backfill matching (branch `corpus-cold-start`, merged 2026-08-11)
The pipeline's **matching** axis, which the tier ladder never addressed. T0→T1→T2→T3 is a fallback ladder for *reading* a document; it has nothing to say about matching what it read to the catalogue. T2 can read "Ivoclar Vivadent AG" off a scanned DoC with perfect fidelity and the document still fails to link, because the join compares that string to the literal `IVOCLAR` derived from BC vendor code 001 — escalating a tier re-reads a value that was already correct. Both tolerance layers are per-manufacturer data, so both live in the playbook. Spec: `docs/superpowers/plans/2026-08-10-backfill-matching.md`, written from a free T0-only measurement of the Ivoclar corpus *before* any paid extraction run.
- **Ordering fix — `discovery.hold`.** RESOLVE necessarily runs before BACKFILL (it builds the `item_group`s a `group_id`-null backfill document resolves against), so at a first ingest nothing is covered yet, C3's "already has a current doc or staged candidate" suppression cannot fire, and every group web-searches for documents already sitting in `imports/dentalia-sftp`. `discovery.hold` (env `DISCOVER_HOLD`, default off) breaks the ordering: RESOLVE builds groups and emits no `discover.group`, the local corpus is mined, and discovery then runs against a registry that knows what it already has. Held emissions are counted as `discover_held` on the job result — the hold and the C3 case both leave `emitted_discover` False, so without a separate counter the report could not say which happened, and nothing skipped is silent. Reversible by construction: the discover dedupe key carries a constant cycle and dedupe is active-scope only (invariant 8), so `cli regroup --apply` after dropping the hold re-enqueues `resolve.group` and discovery fires for exactly the groups the corpus did not cover. Matching registry reset: `tools/cold_start_reset.sql` — `item_mirror` is in its truncate list deliberately, since INGEST emits `resolve.group` only for rows whose comparand tuple changed, so truncating `item_group` alone would leave those items mirrored, groupless and counted nowhere.
- **Blocker 1, manufacturer (2026-08-10, with a follow-on the next day).** VALIDATE now canonicalizes the extracted manufacturer through `manufacturer_alias` before the group lookup — read-only, unlike RESOLVE's self-seeding version, so a garbled OCR name can never mint a manufacturer; a miss falls back to the raw string. Zero groups under the canonicalized name flags `manufacturer-unresolved` instead of leaving the failure to be inferred from an empty link list. The follow-on fix found the raw-string fallback still hitting a **case-sensitive** group compare: `GC Europe N.V.` (document) resolved to 0 groups while 95 groups carry `GC EUROPE N.V.`, so all 149 GC documents covering 359 catalogue items lost. `_normalize_manufacturer` now folds case, whitespace, punctuation-adjacent spacing and accents (NFKD, strip combining marks) on both sides of both lookups. **Folding only, never fuzzy** — measured: at `token_set_ratio` 80 the registry's 370 manufacturers collide 30 times and ~28 are wrong merges (`OCO`/`VOCO` 85, `FARMADENT`/`FORMADENT` 88, `MEDIAS`/`MEDIS` 90), and a wrong merge attaches one company's certificate to another company's product. No legal-form token is ever deleted, so `DENTSPLY Implants N.V.` and `DENTSPLY Implants Manufacturing GmbH` stay distinct groups.
- **Blocker 2, REF.** Manufacturer DoCs enumerate market/region variants of an article number (digits + 1–3 trailing letters, e.g. `645986DC`); BC records only the base number. Measured over 174 Ivoclar corpus PDFs: exact REF matching links 19/174 documents, stripping 1–3 trailing letters links 54/174. A global strip would corrupt manufacturers whose letters are load-bearing (Komet's space-containing ISO bur codes are the documented case), so `ref_normalize` is a **per-manufacturer playbook key**, distinct from the existing `ref_strategy` (a parsing concern, not a matching one), authored for Ivoclar only; every other manufacturer gets the identity function. Applied at comparison time to both sides — stored `mfr_ref` and extracted `ref_list` are never rewritten. Mutation-tested: reverting the group lookup to case-sensitive kills 4 tests, dropping REF normalization kills 1, applying it without playbook scoping kills 1 (encoding the Komet-safety requirement directly in a test).
- **Contract sync.** `manufacturer-unresolved` had been live in code and absent from both the PRD's flag→disposition list and the handbook's two enumerations — precisely the drift the contracts exist to prevent, with the backfill about to make it a common outcome. Recorded with its disposition **verified against `gate.py` rather than assumed**: `BLOCKING_FLAGS` is `("older-than-current", "no-item-identifier")` only and production additionally requires *no* flags at all, so the new flag caps at `staged`. Deliberate — a document whose manufacturer we cannot place is still real and worth archiving, and it stages with zero links rather than being dropped. PRD rule C1 now also states what the scoping lookup actually does (read-only alias canonicalization, both-sided folding, the owning manufacturer's `ref_normalize`), and the no-fuzzy decision is recorded with the evidence that settled it so it is not re-argued later.
- **Test-infra fix, worth its own line because it cost a false regression hunt.** `tests/conftest.py` hardcoded `TEST_DB = "dentalia_test"` and opened each session with `DROP DATABASE ... WITH (FORCE)` + `CREATE`; the env overrides did not cover the DROP/CREATE, so two sessions could not run pytest at once — the second to start forcibly killed the first's connections and recreated the database underneath it mid-run, and the victim reported setup errors and mid-run failures indistinguishable from a real regression (observed 2026-08-10 as clean / setup-errors / mid-run-failure across three consecutive runs). `TEST_DB` now defaults to `dentalia_test_{pid}`, honours `DENTALIA_TEST_DB`, and every connection URL is built from it through one `_with_db()` — two places free to diverge was the actual defect, not the hardcoded name. Verified by running two full suites concurrently (distinct databases, both green). Closes `[test-db-collision]`; leaves `[stale-test-db]` (a run killed before teardown leaks its database).
- **Measured, not fixed:** `[validate-refgate-n1]` — `_ref_gate_for_group` issues one `item_group_member` query per candidate group (VOCO 25 groups = 28 ms, GC 95 = 75 ms, IVOCLAR 194 = 132 ms per document; roughly 13 ms fixed plus 0.6 ms per group). The N+1 **predates** the normalization work. Harmless for a 1,307-document backfill (~80 s total), real for Zagreb's ~100k items.

### Out-of-band — GC pilot: the first paid corpus run (2026-08-12)
The GC brand folder was run through `backfill.scan → extract → validate → gate` against the live API — the first time extraction ran anywhere but an operator's shell. Almost nothing in this section is a feature; it is the list of things that only fail when a real run happens. Audit of the same day: `docs/project-audit-2026-08-12.md`.

- **The archive was never an archive.** `backfill.scan` stored `str(path.resolve())` as `archive_url` — a path on whichever machine ran the scan, invisible to the worker, different in the web container, and destroyed by the next SFTP re-dump. End-state output 2 did not exist. The scan now archives through the `StorageAdapter` and hashes the bytes it actually stores; `imports` is mounted read-only into `worker` so the scan runs where it belongs; the handle rides the payload through `extract.doc → validate.doc → gate.candidate` instead of GATE re-deriving it from `fetch_log` (which holds the *source* path by design); and GATE heals `evidence.archive_url` as well as the document's, since invariant 2 makes the handle part of every value's evidence — verified live at 130/130 documents and 731/731 evidence rows with extraction cost unchanged, so nothing was re-extracted. The one-off repair of the 57 pre-existing rows located bytes **by content hash**, not by the stored (broken) path. It took an explicit invariant-1 exception and was **rejected and deleted** the same day on Denis's ruling: the bug is fixed at source, and ratifying an exception for dead code buys a permanent hole in the one invariant write-confinement rests on. Invariant 1 is absolute again.
- **`coverage_scope` `item` retired, then made structural (migration `022`).** `derive_coverage_scope` already produced what the committed ground truth says but stamped it 0.9 against a 0.95 threshold, so it escalated on every document and the model overwrote a correct deterministic answer: 37 of 57 registered documents carried `item`, a value the ground truth never assigns. `item` cannot be produced honestly — a DoC listing one article and a DoC listing forty are structurally the same document, and the regulator permits either — and "covers exactly one article" is `len(ref_list)`. Migration 022's CHECK makes the two-value vocabulary structural; adding it turned 68 tests red, every one a fixture asserting a value the registry may no longer hold (including `seed_ui`'s `coverage_scope: str = "item"` default, which fed most of the web suite — that latitude is how 37 real documents acquired it).
- **`ref-catalogue` barred from production (migration `021`).** The basis a backfill document forms when it matches REFs against the whole catalogue with no manufacturer to scope the lookup. Link-level cap, same structural posture as `name-family`/`fetch-context` (invariant 3).
- **The worker could not extract at all.** 79 of 149 extractions died on "Could not resolve authentication method": `ANTHROPIC_API_KEY` appears in no commit of `docker-compose.yml` on any branch, and extraction had only ever run on the host where the operator's shell loaded `.env`. Compose now passes it as required (`${VAR:?}`), the client is constructed *with* the configured key rather than relying on the SDK's env lookup, and the worker refuses to start without it — one error at startup instead of 79 dead jobs twenty minutes in. Separately, four times that day an image built before a change ran old code and reported success (including `cli migrate` answering "up to date" for a migration absent from the image); `app/version.py`'s `source_fingerprint()` hashes `app/**/*.py` + `migrations/*.sql` at runtime, path-independently, so `python -m app.cli version` answers identically on host and in-container, and the worker logs it in its first line.
- **Extraction defects the corpus found.** GC's multi-page article table stitched (with the REF-column chooser shared rather than re-implemented) and the stitched scan stopped latching onto a table that yields no codes; Basic UDI-DIs and prose kept out of `ref_list`; an ISO certificate allowed to carry `regulation` `'n.a.'` instead of being rejected as incomplete twelve lines before the C4 binding rule written for it; the **batch** transport stopped erasing an earlier tier's hit with a raw `fields.update` (the sync ladder had been fixed on 2026-08-11 and the transport had not — the same 26-of-61 loss on the transport the sweep is mandated to use); NUL bytes stripped where PDF text enters the process rather than at each write site; the archive filed under the scanned brand folder rather than the brand's internal subfolders; and a scan that finds nothing now **fails** instead of reporting a clean `scanned: 0` indistinguishable from a fully-ingested corpus. `EXTRACT_MODE` and `DISCOVER_HOLD` are both declared in compose so the two cost-bearing switches are visible where the stack is defined.
- **The staging band that hid a third of the catalogue.** RESOLVE staged a suggestion for a name score in `[suggest, accept)` and wrote **no** `item_group_member` row, while every REF-gate path in `validate.py` joins through that table — so 5,831 of 15,958 items (36.5%) were invisible to document linking entirely, and perversely a *worse* match stayed reachable (below `suggest` an item gets a singleton; inside the band it gets nothing). Setting `name_suggest = name_accept` collapses the band; what it bought was product-family pooling for DISCOVER, which is held anyway. Reversible by lowering the threshold and re-running `regroup`. `load_config()` carried its own hardcoded 0.72 — changing the dataclass default alone would have read correctly in the source and changed nothing at runtime. Re-resolving then exposed that `_resolve_open_suggestion` ran only on the two human branches, so a grouped item could carry an open suggestion forever; both automatic paths now clear it (`decided_by='system'`, idempotent).
- **The review board.** `/staging` returned 7.83 MiB of HTML, 7.58 MiB of it 5,831 grouping-suggestion rows rendered expanded; both sections now paginate at 50 and load row detail on first expand (65 KiB). Every "file" link in the UI was dead — templates rendered `archive_url` (a storage handle) into an `href` — so `/documents/{doc_id}/file` resolves the stored path against configured roots, with a sha256-verified tail search as the only fallback, so a same-named decoy cannot be served as a compliance document. The board was rewritten for compliance staff rather than the pipeline team (flags as sentences, an unmapped flag degrading to visible text and never to silence, one-click approve/reject outside `<details>`, an `edit_baseline` so only genuinely changed fields reach `edits` — each one writes T3 human evidence that permanently outranks the extraction it replaces). ### Out-of-band — C12, extraction correctness, and full-coverage linking (2026-08-13)
The work between the pilot and the paid sweep. One client ruling changed an invariant's comparand; everything else is the difference between a document being read correctly and its reading reaching the right items.

- **C12: the REF gate matches the catalogue's own article number (migration `023`).** Client answer (restated 2026-08-13): the supplier article number "ni tako pomembna" — the primary item number is the key, because that is what is printed on the physical article. - **REF-list integrity.** The prompt caps `ref_list` on the premise that "a deterministic parser enumerates the full list"; nothing enforced it, and `merge`'s "a different, non-empty later value still wins" then stored the capped LLM sample **over** T0's enumeration — measured at 1,502 codes stored where T0 reads 2,843, across 21 documents, the missing codes reaching 199 more catalogue items. `merge` gains one exception scoped to `_ENUMERATED_FIELDS`: a later tier may not **shrink** a non-empty enumeration (longer wins whichever tier found it; lists are never unioned, because evidence carries one verbatim/page/tier per field). The prompt cap went 40 → 100, then to 150 on the measured distribution (median 4 codes; cap 150 truncates 1 of the 125 GC documents that yield a list, and that holdout is document 235 at 1,121 codes, exactly the case T0 exists for). The model's own accounting cannot detect truncation: document 258 claimed "total of 44 codes listed, first 40 returned" while returning 46 against a true 53.
- **Link retraction (migration `024`).** GATE only ever upserted, so coverage could grow and never shrink and a corrected reading could not take back a wrong link — on a compliance registry, the wrong direction of error. Document 235 is the proof: rev 1's truncated REF list resolved to one manufacturer and wrote 19 links; rev 2, repaired to the real 1,121 codes, spans two manufacturers, correctly flags `multi-manufacturer-ref` and carries zero links — and rev 2's gate job ran *after* rev 1's with the 19 still standing. Registry-wide 21 of 134 links were stale. New status `retracted`, distinct from `rejected` (which records a human saying no), append-only, one audit event each, and **staged links only** — production means a human approved or bound it, so auto-retracting one would silently undo a human decision. A stale-rev guard additionally stops a superseded candidate writing at all, since `repair-ref-list` appends a rev and re-emits, so two candidates for one document can be in flight. Seven coverage reads then had to learn that a retracted link is not coverage — the JSON API needed no change, reading `item_document_production` by construction.
- **`ext.manufacturer` shipped — closes the 2026-07-13 open end.** Nothing produced identity for a corpus document, so VALIDATE's scoped path could never fire: 0 of 159 extraction attempts carried the key. The LLM half adds `manufacturer` to `TARGET` (nine fields → ten), to `_ESCALATE_ALWAYS` rather than `_ESCALATE_ITEM_ID` (item-id fields are suppressed for a manufacturer-scope cert, and identity is the one thing such a document *does* assert — which is exactly why every mfr-binding task read "manufacturer unknown"), to the structured-output schema, and to both prompts, which now bar the **authorised representative** explicitly (66 corpus files name Dentsply IH Limited, always as the rep). The T0 half matches the playbooks' declared legal names against the document's own text, with three measured guards: names under 6 characters are never identity (GC's alias is the bare string "GC"), two different manufacturers in one document abstains rather than picks, and confidence sits at 0.9 *below* the 0.95 escalation threshold on purpose — T0 proposes cheaply, the LLM confirms. Deliberately **not** `match.anchors` (they would resolve a Straumann DoC to KOMET) and **not** the folder name (that is the supplier). Tier parity became a contract in the same commit: `T0_PRODUCED` and `T0_EXEMPT` must partition `TARGET` exactly — T0 had been silently skipping `referenced_docs`. Measured against the live candidates, identity unlocks 51 `ref-catalogue` documents and 3 blocked by `multi-manufacturer-ref` (~209 items); the 73 `no-ref-overlap` documents are correctly not helped.

Invariant 2 governs what a *production* value must carry, so the gap now raises the blocking flag `evidence-page-missing`: archived, evidenced, routed to manual review, production unreachable. No value, or no verbatim/tier/confidence, still hard-errors — those leave nothing to review.
- **A signing date is not an expiry (2026-08-12).** Document #239 carried `validity_to` 2026-02-12 with verbatim "Leuven,12/02/2026" — the place-and-date line MDR Annex IV point 10 requires on every declaration. Three of ten extracted dates were this, all T1 at 0.75–0.85, so **3 of the 5 documents on the expiry board were false alarms**. Instructive root cause: `validity_from` carried the "NOT the issue / signing / print date" warning and `validity_to` carried none, so the guard on one field pushed the error into its unguarded neighbour. **Half of that fix was reversed the next day (Denis's ruling 2026-08-13)** and the entry above is kept as written because the reversal is the interesting part: warning *both* fields off the issue date left 0 of 127 declarations carrying a start date, so every supersession decision fell to `downgrade-uncomparable` and landed on a human — and T0's `_FROM_LABELS` had always disagreed, so the deterministic tier already implemented the right rule and the LLM tiers overrode it on escalation. The surviving asymmetry, now stated explicitly in both prompts and regression-tested: a place-and-date line is never `validity_to`, and an uncertain date belongs in `validity_from`, because an issue date stored as an expiry makes a valid document read as expired while an issue date stored as a start is at worst harmlessly early. The three affected documents (160, 227, 239) were re-extracted and now carry `validity_to` null. A deterministic guard is still owed (`[validity-date-guard]`), minus its withdrawn check 3.
- **The schema the API actually accepts.** Every extraction was broken from 2026-08-13 until this fix — two stacked 400s (a nullable enum declared as an `enum` beside a union `type`; then 18 union parameters against the API's limit of 16, because a nullable `page` on every field spent 10 of them and the tenth target field tipped it over), neither caught by 1,154 passing tests **because every test asserted the schema dict and not one ever sent it**. The 1,158-document sweep would have failed in full. No tokens burned — a 400 is rejected before billing. Three guards: a walk for the enum-beside-union shape, a count of what the API counts (so an eleventh field fails locally instead of in production), and an opt-in test that actually sends the schema. That last one is the only one of the three that would have caught both, and the compose `test` service now passes `ANTHROPIC_API_KEY` through so it can run there at all — its `environment` block replaces the anchor rather than merging, which is how a schema the API rejects shipped green.

- **The signing date is typed into a drawn blank.** T0's place-and-date reader scored **1 of 30** on GC. The line is a form field: GC prints `Leuven, ……………` and types the date into the dots, giving `Leuven, …10/10/2022…`, `Leuven, 12/02/2026……………`. - **`source_url` had no writer at all.** The column has existed since the schema was written and was NULL on all 141 rows, costing the manufacturer's own filename: the archive keeps only a sanitized form, so `gce_certification_MDR 778483.pdf` is stored as `..._MDR_778483.pdf`. Read from `fetch_log` rather than threaded down three payloads — the ledger is keyed on `content_hash`, which GATE already holds, so it answers on the replay path too, where no live payload exists. Sticky on conflict; a hash with no ledger row still gates and stores NULL, because provenance must never block a write.
- **A dead job now reaches a person.** `manual_kind` has carried `dead-job-followup` since the schema was written and **nothing ever produced one**, so 45 dead jobs were visible only to somebody who thought to open `/dead`. Raised at the dead-letter transition in `queue.fail` so no tag can be forgotten, closed by `queue.finish` when a later job with the same dedupe key succeeds — deliberately *not* by the re-run button, because re-queueing is not success and a job that dies again would have had its alarm cleared by the attempt to fix it. The first implementation put the close in the UI and hit `InsufficientPrivilege`: the web role holds no write grant on `manual_task`, so the producer boundary is enforced by the grant matrix rather than by convention. That is now a test.
- **A superseded reading must not write the document either.** `_is_current_rev` guarded the link writes and nothing else, so rev N-1 could still rewrite type, regulation and dates through the document upsert's `ON CONFLICT DO UPDATE`. It also ended a loop with no exit: two GC safety data sheets carried `coverage_scope: "item"` from before the API schema enumerated the value, and their stale rev-1 candidates replayed that stored value into an INSERT the CHECK rejects — dead-lettering on every attempt **and on every re-run**. Verified closed on the live jobs: both now return `skipped: superseded-rev`, and the worker auto-resolved their two `dead-job-followup` tasks.
- **A declaration that names its certificate is not certless.** Rule 6 read `referenced_docs` alone, so a DoC printing its certificate number on its face counted as citing nothing — while `cert-unresolved`, twelve lines below, had always read both fields. Two rules in one handler disagreeing about what the same evidence means. Cost: **109 documents capped at `staged` carrying scores of 0.97**, a passing REF gate and correct dates. Underneath it sits a premise worth recording — the flag was built on "MDR says a DoC carries no expiry, so one is suspicious", which is true of the regulation and false of this corpus: **110 of 110** DoC expiry dates cite an explicit phrase (`Valid until`, `Gültig bis`, `Scadenza`), zero inferred. IVOCLAR prints real expiries on its declarations; GC does not. Making the flag about an *unevidenced* expiry is `[expiry-flag-should-be-about-evidence]`, deliberately not shipped on one brand's evidence.
- **C15 `filed` — a document that covers nothing we sell (migration `025`).** The investigation that mattered most. Of the 1.605 REF codes the 181 staged documents named, **Dentalia stocks six**. `Cention Forte, Cention Primer.pdf` names six codes returning zero rows in `item_mirror` by either column, with and without the WW suffix; `CENTION` matches nothing by name. **Two claims of mine in this log's earlier sections were wrong and are corrected here.** The 45 dead pilot jobs were reported as 16 lost documents; they are **2 distinct documents**, both safety data sheets that correctly do not belong in the registry, so no work was lost — the count was of jobs, not documents.
