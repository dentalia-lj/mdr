3State machines

stateDiagram-v2
  direction LR
  [*] --> pending: enqueue (active-scope dedupe)
  pending --> running: claim, attempts+1
  running --> done: finish (frees dedupe key)
  running --> pending: defer (batch poll, attempt refunded)
  running --> failed: error (exp backoff)
  running --> pending2: visibility timeout 300s
  pending2: reclaimable
  pending2 --> running
  failed --> running: retry after run_after
  failed --> dead: attempts exhausted
  dead --> running: UI re-run (same key, interactive)
  done --> [*]

Job lifecycle. done and dead free the dedupe key (C2): re-enqueue is normal, not a schema fight. All live.

stateDiagram-v2
  direction LR
  [*] --> staged: gate (score below HIGH or flagged)
  [*] --> production: gate (HIGH + ref_gate + no flags)
  staged --> production: approve / bind / high-score redelivery
  staged --> rejected: reject
  production --> production: never downgraded (CASE guard)
  superseded: superseded (enum value, NEVER written - C6 inert)

document.status. The red flag here: a same-hash re-extraction at a new rev overwrites a production row's field values (evidence stays old rev).

stateDiagram-v2
  direction LR
  [*] --> staged: any basis
  [*] --> production: trusted basis + doc production + HIGH
  staged --> production: approve, trusted bases only
  staged --> staged: fetch-context / name-family, forever (C5 CHECK)
  rejected: rejected (enum value, no writer today - severance unimplemented)

item_document.status. Consumers see a doc for an item only when doc AND link are production.
