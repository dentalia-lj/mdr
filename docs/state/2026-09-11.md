## The outage, and its cause

`dentalia-postgres-1` failed every start with `PANIC: could not locate a valid
checkpoint record` from 06:52 UTC (97 restarts by 08:24). Cause, read from both
containers' logs: `docker-compose.yml:76` defaults `PGDATA_HOST` to
the registry bind mount, and the worktree `playbooks-into-db`
never set it, so its `postgres` container bound the **same data directory**. The two
servers reached "ready" within seconds of each other on 08-27 20:09, 08-27 20:14 and
08-31 08:35, and both ran from 08-31 08:35 to 09-09 15:09:37. At that shutdown the
main server wrote its checkpoint at `8/614E5AE0` (15:09:37.925) and the worktree's
wrote `5/61E904E0` (15:09:37.956); every start since failed on it. The worktree
server also wrote **27.854 buffers** into the shared directory across 76 checkpoints,
27.848 of them on 08-27.

Repaired out of band: snapshot to `<PGDATA_HOST>-snapshot-2026-09-11`
(08:32), WAL reset (08:33:16), ready 08:33:41. Checked since: `pg_dump -f /dev/null`
reads all 63 MB without error, so heap and TOAST pages are readable, and row counts
line up with 09-04 plus a week's work. **Not checked: the indexes** — `amcheck` is not
installed (`pg_extension`: `plpgsql`, `pg_trgm`). Still live: the compose default is
unchanged, `playbooks-into-db-postgres-1` still exists (exited, `restart:
unless-stopped`), and **21 of the 22** worktrees with their own `docker-compose.yml`
set no `PGDATA_HOST`. The comment at `docker-compose.yml:20-22` recommends
`COMPOSE_PROJECT_NAME`, which renames containers and leaves the bind path alone.

Nothing alerted. `health-watch` is a queue job and the worker could not connect;
`alert_state` holds 0 rows; `/healthz` returns `{"status": "ok"}` without touching
the database (`web/app.py:1986-1990`), so `web` stayed healthy throughout.
