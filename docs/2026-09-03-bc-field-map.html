The six that fill item_mirrormigration 002

Left is what BC sends, middle is the column it lands in, right is the spreadsheet column it retires. Verified by value: fed through BcApiAdapter, these three records produce rows byte-identical to what CsvExportAdapter reads from the xlsx.

One column has no source and one has no consumer. udi is absent from the API and the spreadsheet alike, so nothing is lost by switching; gtin exists but is empty and is a GS1 UDI-DI, not the Basic UDI-DI the REF gate wants. And manufacturer_raw is NOT NULL: it resolves to a bare code like 011 until vendor_master supplies the name, and no endpoint publishes that mapping.

The three we would write back/dataitems, PATCH with If-Match

Not in the base offer. Ground-truth decision 9 says no writeback to BC except file references, so this is annex scope, and two of the three need a Dentalia ruling before a single PATCH is safe to send.

Carried, not wired

Real signal the spreadsheet never had. The first group is sync mechanics we would need for a live connection; the second is context worth having once, or worth understanding before someone mistakes it for something it is not.

The rest

Stock, costing, planning, warehouse, posting groups and two extension prefixes. Nothing here touches compliance. Listed in full because this is what $select would drop: keeping only the ten fields we use takes a full sweep from 112 MB to 5,6 MB.
