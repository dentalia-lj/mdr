Solid arrows: the normal chain. Dashed: conditional or human-mediated. Every enqueue goes through app/queue.py — 26 queue.enqueue( call sites across 14 modules, writing 22 literal dedupe format strings that reduce to exactly the 18 shapes PRD §0's conventions table lists (resolve: ×2, resolve:manual: ×2 and validate: ×3 are the same shape from different producers). The shipped stack holds discovery: docker-compose.yml:112 sets DISCOVER_HOLD: ${DISCOVER_HOLD:-true}, so RESOLVE builds groups and emits no discover.group; the corpus is mined first and discovery runs later against a registry that knows what it already has. The config default is False (app/config.py:152) — compose, not the app, is what makes the hold the norm.

An unknown kind raises.
  • data_anomaly (019) is (kind text, subject text, catalogue, detail jsonb, seen_count, first_seen, last_seen) with UNIQUE (kind, subject) — a repeat observation bumps the counter rather than inserting.

3State machines

stateDiagram-v2
  direction LR
  [*] --> pending: enqueue (active-scope dedupe)
  pending --> running: claim, attempts+1
  running --> done: finish(result) — job.result + finished_at
  running --> pending: defer (batch poll, domain lease)
  running --> failed: error (exp backoff)
  failed --> running: retry after run_after
  failed --> dead: attempts exhausted
  dead --> mt: raises manual_task('dead-job-followup')
  mt: manual queue
  dead --> running: UI re-run, singly or by error group
  done --> [*]

Job lifecycle. The partial unique index covers pending|running|failed only, so done and dead both free the key — that is what makes a monthly re-check an ordinary enqueue. Two handlers self-defer rather than finish: EXTRACT while a Batch API job is unfinished, FETCH while another worker holds the domain lease.

stateDiagram-v2
  direction LR
  [*] --> staged: below HIGH or capped by a flag
  [*] --> production: HIGH + ref_gate + nothing gating
  [*] --> superseded: fast path (older, all four guards pass)
  [*] --> filed: bound, covers zero catalogue items
  staged --> production: approve / bind / high-score redelivery
  staged --> rejected: reject
  production --> superseded: a newer doc supersedes it

document.status — five values (doc_status, 005 + 025). The upsert's status CASE makes production and superseded sticky, so no re-delivery can downgrade or resurrect a row. filed is a settled disposition, not a waiting room; nothing re-links a filed document if its item is later stocked (filed-relink, deferred deliberately).

stateDiagram-v2
  direction LR
  [*] --> staged: any basis
  [*] --> production: trusted basis + doc production + HIGH
  staged --> production: approve, trusted bases only
  staged --> staged: name-family / fetch-context / ref-catalogue, forever (CHECK)
  staged --> retracted: current rev no longer supports it
  production --> rejected: human reject cascades every link
  staged --> rejected: human reject cascades every link

item_document.status — four values (link_status, 005 + 024). retracted means the machine's own evidence moved; rejected means a human said no. Only staged links are ever auto-retracted: a production link means someone approved it, and retracting one would silently undo a human decision. Append-only either way — the row and its match_basis survive, each transition its own audit event.
